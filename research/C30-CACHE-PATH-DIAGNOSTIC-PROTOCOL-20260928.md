# C30 cache-path diagnostic protocol

- Objective: identify why the same frozen two-turn 8K workload reused 2036 server tokens in C28 but only 35 in C29. Base `bfd0802`; backend/model/build remain the original pinned control. C28/C29 FAILs are preserved. This is an instrumented diagnostic, not a timing confirmation.
- Source alternatives: `server_tokens::get_common_prefix` may observe an early token mismatch in the actual slot/input sequences, or the SWA/checkpoint branch may reduce an initially long `n_past` because required KV state is absent. The official `/apply-template` ID arrays agree across C28/C29, but are insufficient to select between these runtime paths.
- Freeze: `LLAMA_SERVER_SLOTS_DEBUG=1` and server `-lv 4`, with identical synthetic first user/assistant/second user messages, original backend, P12, n_ctx8192, E18 zero swap, CPU100 and all prior guards. Source logging is allowlisted and recorded in the protocol. d1 runs; d2 is available only if d1 passes the cache gate and leaves the miss unexplained. Maximum two fresh starts, each with thermal admission. First observed actionable miss stops the unit.
- Decision gate: inspect raw stderr for the printed old/new token boundary and the trace branch that forces prompt reprocessing; compare with official IDs and `cache_n+prompt_n`. A missing or ambiguous log yields INCOMPLETE_DIAGNOSTIC, not an inferred cause. No instrumented timing enters a speed claim. C15 source-only, M3 partial, M4 NOT_RUN, default unchanged.
