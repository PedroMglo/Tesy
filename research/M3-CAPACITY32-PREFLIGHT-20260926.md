# M3 prospective 24 versus 32 slots on target

Objective: test whether more of the measured repeated expert reads can be avoided by enlarging only the existing per-layer slot pool from 24 to 32. Evidence entering this experiment: three prior 16/24 alternating A/B pairs gained 24.0% mean decode and reduced sampled process `read_bytes` by 19.3%; the 24-slot continuous task run still had an estimated 612.258 MB process read accounting per decode token. This is optimization/configuration intervention **4/6**, with no backend source change. Base lab commit `33c4804`, target GGUF/full SHA and backend SHA identical to M3; the underlying 24-slot source tree remains clean. The source has 128 experts/layer, so 32 slots remain below the expert set.

The 32-slot nominal encoded cache adds 2,961,100,800 bytes on 28 CPU layers and 846,028,800 bytes on 8 GPU layers compared with 24 slots. Prior 24-slot peaks were roughly 11.5–12.0 GB cgroup and 3112–3123 MiB total GPU. This estimates feasible headroom under the same 18 GiB/zero-swap host scope, RSS17 GiB, GPU7000 MiB and MemAvailable6 GiB watchdog; observed peaks remain authoritative. No storage/layout, quantization, routing, expert selection, kernels, GPU placement, batch, context, sampler, preload or request policy changes.

First gate: same GPU8 four-token Harmony prefix on 24 and 32 slots, 201,088 complete final logits bitwise equal, finite, same token IDs, no resource event. The 24-slot probe may reuse its previously saved row only if the binary SHA and model identity match this 32-slot probe; otherwise run a fresh 24-slot probe. If the gate fails, do not execute timing A/B.

Second gate: same `workloads/m1_two_turns.txt`, two requests in one process, context4096, batch256/microbatch32, eight threads, greedy seed42, no preload/repack, direct expert reads, GPU8. Compare 24/32 slots in alternating order, prospectively `32,24,24,32,32,24`, with new run IDs and process per run. Primary metric is aggregate backend decode tok/s across both requests, with per-request rates reported. Secondary metrics: total elapsed, sampled process `read_bytes`, cgroup/GPU peaks, swap/OOM/max events, identical generated output and task checks. A gain is promoted only if it is reproducible across completed pairs and correctness/resources hold. If the first 32-slot run fails correctness or resources, stop. If the remaining time budget prevents three pairs, mark fewer observations exploratory. The prior 16/24 pair is not silently mixed into this causal comparison. No threshold is relaxed after outputs. Raw logs/samples remain local; manifests, compact comparison and decision are publishable.

Stop at the earlier of the original cumulative four-hour active-work cap, six interventions, resource failure, backend error or unexplained output difference. The run is not needed to preserve the established >=2 tok/s target and does not by itself prove a sustained new M5 rate. Tests: NOT_RUN at freeze.
