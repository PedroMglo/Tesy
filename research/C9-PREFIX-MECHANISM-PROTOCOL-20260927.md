# C9 exact-prefix mechanism screen

- Objective/base: determine whether the pinned original server, P8 native preload ON, one 8K full-SWA slot, actually reuses a common token prefix and reduces incremental prefill. Base evidence: `c9-g1-init` and `c9-g2-forward` admitted under E18; commit `4547d9f` is the last evidence checkpoint. Backend/model and all runtime flags stay fixed. The only request-level variable is `cache_prompt` on the second request.
- Hypothesis/alternative: `cache_prompt=true` reuses at least 450 exact IDs from a synthetic approximately 512-token prompt extended by approximately 128 IDs; alternatively slot/KV/SWA behavior forces reprocessing or cache bookkeeping costs erase latency savings. This is a mechanism diagnostic, not natural chat session quality.
- Inputs/freeze: `prefix-input02.json` fixes the literal synthetic text, temperature zero, seed 42 and cap four output tokens. A model-free estimate based on the observed C9 template overhead showed that the original 490 repeats would likely exceed the frozen first-prompt range; input/protocol01 were preserved without model execution, and 445 repeats were frozen prospectively in input/protocol02. The embedded model template/tokenizer runs on both requests before either response in each process; raw token IDs and SHA hashes are saved before outputs. Actual first/second prompt counts must be 480–540 / 600–700, common prefix at least 450 IDs, and prompt plus cap within 8192. No external Harmony reconstruction. ON and OFF protocols pin source, binary, mapped-library expectations, model stat and full argv.
- Execution/decision: one diagnostic pair, order cache ON then cache OFF, fresh server process and fresh E18 scope per arm; each arm runs the same first request with caching ON and the extended second request with its assigned cache setting. Require `cache_n=0` on first requests and OFF second; ON second must show `cache_n>=450` and never exceed actual common-prefix length. Full resource/identity/raw/sample gates and API/backend token/timer reconciliation apply. Report second-request prefill paired gain `100*(OFF−ON)/OFF`; a gain >=50% is a favorable investment signal, not confirmation. Require first-request message/usage equality before attributing the pair timing; otherwise call timing INCONCLUSIVE while preserving the cache observation. Do not infer sampling distribution or bitwise full logits from API text.
- Limits/alternatives: expert pools may be warm after the first request within each process; page cache is uncontrolled, and the two-arm order does not establish a replicated causal speed claim. Source `ready_on_arrival` and `/proc/PID/io` remain diagnostic. A valid negative cache observation changes the next hypothesis; a resource/evidence failure ends the affected unit without retry. Cold512 product target, 2048/4096 true conversation prefixes, 7936+256 boundary, 12-task quality and sustained20 are NOT_RUN here. Usual service/default unchanged.
