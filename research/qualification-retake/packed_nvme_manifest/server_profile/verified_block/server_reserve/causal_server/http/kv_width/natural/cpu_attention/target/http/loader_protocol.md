# Identificar os dados do carregador na qualificação do ELF serial

O preflight OFF R01 acabou por SIGTERM durante o arranque. O auditor recusou o basename `ld.so.cache`. O journal glibc do mesmo PID menciona o caminho /etc/ld.so.cache. O mapeamento original não foi guardado com as permissões, o dispositivo e o inode. R01 conserva o seu FAIL e os quatro braços HTTP continuam por executar.

Congelar uma nova identidade para distinguir o ficheiro de dados glibc das bibliotecas. Usar exclusivamente o caminho canónico /etc/ld.so.cache, ficheiro regular de root sem escrita para grupo/outros, magic glibc e SHA-256 `6b735fd19e8fcb2d9f5b6e0523a260ccf8a497e5210d998e9acbcbd29baef21c`. Fixar stat e chave VMA por observação de uma página do mesmo ficheiro no mesmo host. Reconhecer no processo apenas a extensão total arredondada à página, offset zero, permissão privada só de leitura, dispositivo e inode observados e nome integral. A lista de bibliotecas e as provas de identidade, inicialização e resolução de símbolos continuam as do protocolo HTTP.

Primeiro executar uma fixture fora do modelo com o mmap real de leitura e uma biblioteca real do próprio processo. O auditor histórico deve rejeitar o mapa com os dados glibc; o corrigido deve produzir exatamente a mesma lista de bibliotecas que o histórico produz sobre a biblioteca sozinha. Exigir rejeição dos controlos de nome, inode, dispositivo, extensão, permissões de execução/escrita e unlink. Reabrir o journal e provar que R01 não tem um resultado numérico nem pedido HTTP. A fixture admite uma nova tentativa OFF no máximo, com o mesmo binário, C55 ainda vigente, novo C118, E20 e os mesmos limites de 320 s e 128 MiB. Rejeitar qualquer falha ou alteração do ficheiro. A campanha HTTP mantém a ordem e o orçamento do protocolo original.
