Objective: run exact-routed GPT-OSS expert streaming under a controlled host budget, compare stock and candidate, then bring up the real 120B if a compatible artifact is available. Tesy base commit/tree at start: `7041b39ec42948e6d394e151974940750ba9b070` on `research/numerical-characterization-ab-20260925`, with unrelated pre-existing `.vscode/` untracked. Lab backend source is unmodified: stock SHA `4b1a27fa0eb875bbca4f6cfe936e3d65adc685c0`, candidate SHA `1248fd8fa8cfebaece5ea992e4d951c1e18bb9d5`. Lab is a separate nested Git repository because the preferred sibling path was outside writable roots.

## State and evidence class

Main state: **MODEL_ARTIFACT_REQUIRED** for M4. M0_BACKEND_SELECTED and M1_OVER_BUDGET_END_TO_END were demonstrated **only on the 20B surrogate**. M2_IO_ACCOUNTED, M3_MEASURED_OPTIMIZATION, M4_REAL_OVER_RAM_MODEL, M5_PERFORMANCE_TARGET_MET and M6_LARGER_MODEL_TASK_ADVANTAGE were not demonstrated. The 120B native safetensors exist locally, but the selected llama.cpp streaming loader consumes GGUF; the compatible 120B MXFP4 GGUF is absent. No conversion or download was done.

Measured host: physical Fedora host verified outside the sandbox (`/proc/1/comm=systemd`), Ryzen AI 9 HX 370, RTX 4060 Laptop 8188 MiB, NVIDIA driver 615.71.09, CUDA toolkit 13.3.73, internal NVMe `/dev/nvme0n1p3` btrfs for model and lab. Stock and candidate built with GCC 15.3.1 and CUDA architecture 89. Initial GCC 16 CUDA configure failed because NVCC rejects GCC >15; this remains a recorded failure. No privileged system changes. The scope test confirmed cgroup `memory.max` and `memory.swap.max=0` work on the host. A normal sandbox command cannot access `/dev/nvidia*`; all model runs below used host scopes, not sandbox measurements.

The 20B artifact is the local GGUF at `~/.local/share/tesy/models/gpt-oss-20b/gpt-oss-20b-mxfp4.gguf`, 12,109,564,352 bytes, revision `a7443ebb00ba299cbbbf7e9b69487670447ae8c0`, full SHA-256 verified as `52f57ab7d3df3ba9173827c1c6832e73375553a846f3e32b49f1ae2daad688d4`. All generation used greedy temperature 0, seed 42, context 4096, `n_batch=256`, `n_ubatch=32`, 8 CPU threads, same two public prompts from `workloads/m1_two_turns.txt`, default embedded chat template and reasoning settings, one parallel sequence. No predictor or speculative decoding. Prefix probes used the explicit 17-token Harmony prefix printed in their stdout; they are narrower diagnostics.

## Integrity and numerical correctness

Source audit: the candidate intercepts gate/up/down expert **weight** tensors only and creates a 16-slot pool per layer in the chosen runs. Biases and other original-ID tensors retain logical expert IDs in the graph; only expert GEMM IDs are remapped to physical slots. For `ubatch=32`, wave prefill has 83 non-empty waves in the short prefix. This is source evidence, not a full formal lifetime proof. Candidate log and an in-process file-descriptor check confirmed O_DIRECT expert reads. The descriptor check saw one direct GGUF descriptor throughout generation after the initial buffered descriptor closed; no O_DIRECT fallback was logged in fixed-prefix probes.

An initial CPU logits comparison **failed**: max absolute difference 0.306599 and RMSE 0.057832 across 201,088 logits. The plain path used `CPU_REPACK` for MXFP4 expert weights; streaming used the CPU buffer. A separate configuration with `--no-repack` on both sides yielded **bitwise equality of all 201,088 final-prefix logits**, for both `ubatch=1` and `ubatch=32`. The `ubatch=32` stream run made 440 cold expert misses during that prefix. These are measured equality claims for one fixed token prefix, not all possible inputs.

The first GPU8 comparison also **failed**: max absolute logit difference 0.408554. Streaming automatically disabled op offload because its host cache changes, whereas plain kept it enabled. A new comparison with op offload disabled on both sides, no repacking, direct loader and `ubatch=32` produced **bitwise equality of all 201,088 logits** for the same prefix. This does not certify every GPU decode state. One initial GPU8 plain run hit its 16 GiB cgroup limit: `memory.events max` increased 1271, apparently from a 7.93 GiB `CUDA_Host` buffer plus file cache. This failed run is retained in `results/cand20b-gpu8-prefix-plain.json`. A new direct-loader diagnostic stayed below its 12 GiB cap.

For a longer CPU causal check, the two response texts from candidate streaming and candidate plain with `--no-repack --no-mmap` matched byte for byte, including their natural EOS after 195 and 193 decode tokens. The answers were 391 and `{"city":"Porto","day":26,"amount":14.20}`. This is greedy-sequence equality, separately from the fixed-prefix bitwise-logit claim. GPU8 generated both correct final answers but its second free generation differed in reasoning length from the CPU run; that is not a numerical parity test.

## M1 controlled residency and resources

The CPU streaming run `stream20b-m1-two-turns01` had **9 GiB** `memory.max` (9,663,676,416 bytes), `memory.swap.max=0`, peak cgroup `memory.current` 7,348,518,912 bytes, peak RSS 7,294,763,008 bytes, page-cache `file` peak about 40 MB, zero runtime swap and zero cgroup max/OOM events. GPU use stayed at idle (23 MiB total). Its per-layer 16/32 expert slots hold 5,076,172,800 bytes of encoded expert weights, less than the complete 10,152,345,600 expert-weight bytes. The GGUF itself is 12.11 GB, above the 9 GiB host scope. Two distinct requests completed in the same process with natural EOS. This meets the controlled-budget surrogate mechanism gate, not physical-RAM-overflow of a 120B model.

Process-attributed `/proc/PID/io:read_bytes` continued increasing after prefill, by approximately 33.5 GB during the first decode and 45.4 GB during the second (boundaries sampled at 1 s), or roughly 172 and 235 MB per decoded token. O_DIRECT plus resident non-expert weights and the small `file` charge support the inference that expert misses caused most of those reads. These are **kernel process read counters**, not exclusively measured physical NVMe bytes and not exact encoded expert payload. The candidate has no measured dynamic RAM tier; ready hits and in-flight hits are combined in its stats. H2D traffic, evictions, padding, per-phase hit rate, device-exclusive I/O and thermal equilibrium remain unknown. Therefore M2 is partial.

The warmed plain mmap run charged only 1.75 GB peak to its cgroup despite about 12.34 GB RSS, illustrating shared page-cache accounting. It was not used as over-budget proof. The no-mmap CPU causal baseline had 12.67 GB cgroup peak under a 16 GiB cap and zero swap/OOM. Both were separately recorded, not substituted after seeing performance.

## Target and next gate

The local 120B native MXFP4 safetensors have seven contiguous-header shards and 65,248,815,744 tensor payload bytes; full-content hashes were not recalculated. Their local HF tree identifies revision `b5c939de8f754692c1647ca79fbf85e8c1e70f8a`. The candidate's GGUF loader cannot consume these files directly. Public HF metadata queried through `hf` identifies `ggml-org/gpt-oss-120b-GGUF`, immutable revision `238abdd290bb874b90a5da1b4549881b7d05c091`, `gpt-oss-120b-MXFP4.gguf`, 63,387,346,208 bytes, published LFS SHA-256 `582bd40f6886200101f4c4ed9f25f3fe80cc14c86e9e2b37746cd8904a0c622d`. This GGUF is **not installed**; metadata is in `results/hf-gpt-oss-120b-gguf-*.json` and the optional user download command is in `MODELOS_A_INSTALAR.md`. Its actual tensor layout and loader peaks have not been measured. Native safetensors estimates in the M0.5 budget must not be treated as exact GGUF capacities.

The task suite `workloads/task_eval.jsonl` was fixed before target evaluation: 2 tuning and 10 held-out synthetic code/SQL/extraction/quantitative/planning cases. It was **NOT_RUN**; neither 120B task benefit nor absence of benefit is demonstrated. No code patch, predictor, prefetch or speculative decoding was retained. Two of six diagnostic optimization/configuration interventions were used, about 40 minutes of active work, below the four-hour cap. The next material experiment requires the verified 120B GGUF artifact, then a fresh capacity check from its actual GGUF tensor metadata, a bounded M4 load/prefill/decode under cgroup with one sequence, and fixed-prefix 120B parity. This is an artifact gate, not a physical no-go.
