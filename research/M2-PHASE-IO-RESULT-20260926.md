# M2 post-hoc process-read phase accounting on target server

Objective: narrow the known accounting gap without a new model run or a backend change. Base lab commit `7611d23`. Evidence class: **estimated phase attribution of measured process counters**, computed from the existing `task120b-stream24-eval01` one-second `/proc/PID/io` samples and server launch/completion timestamps. `tools/analyze_task_io.py` reconstructs prompt/decode boundaries using the backend's per-request timing, linearly interpolates between adjacent samples, and writes `results/task120b-stream24-eval01-io-analysis.json`. The final boundary is 0.110 s after the last sample and uses the last observed counter without extrapolation. Source trace hashes and full model/binary configuration are in the original run manifest. This is not exclusive physical NVMe traffic or an exact per-token trace.

For the ten complete task requests, estimated process `read_bytes` was **556.949 GB during prefill** and **1,404.521 GB during decode**. Dividing the latter by 2294 completion tokens gives **612.258 MB of process read accounting per generated token**. Across individual decode requests the estimate ranges from 564.87 to 671.56 MB/token. All ten request intervals had sampled O_DIRECT model descriptors and zero sampled buffered model descriptors. The full process last sampled `read_bytes` was 2,044.344 GB, also including model load, the separate simple smoke and between-request time. The per-task breakdown and sample-boundary gaps (up to 1.236 s) are in the structured output. Bursty reads within a sample interval can shift phase estimates; no error bar narrower than the sample interval is claimed.

Source audit of the selected backend: each streamed layer has one per-layer expert slot pool allocated in either host or GPU memory (`src/llama-moe-stream.h`, `src/llama-moe-stream.cpp`); there is no separately measured dynamic RAM cache behind a GPU pool. Its generic `n_hit` counter includes a resident slot **or a slot still loading**, while `n_miss` counts issued demand loads. The M2 16-slot diagnostic measured 24,071 hits, 30,063 misses, 397.409 GB encoded miss payload and 124.474 s remap stall, but those totals combine load/prefill/decode and do not split host/GPU residency or remaining wait for in-flight hits. The source's CUDA `ggml_backend_cuda_buffer_set_tensor` calls `cudaMemcpyAsync` followed by `cudaStreamSynchronize` before reporting upload completion (`ggml/src/ggml-cuda/ggml-cuda.cu`), so the CPU worker's return does wait for that upload path; overlap with other compute remains unmeasured. These source findings explain why a claimed adaptive three-tier cache or measured H2D savings would be false here.

Decision: keep M2 **partial**. The phase split strengthens the inference that decode repeatedly fetches expert data and bounds process-attributed read cost for this workload. It cannot supply device-exclusive NVMe bytes, per-tier hit rate, H2D bytes, evictions, wasted prefetch, compute-versus-transfer overlap or a physically unavoidable miss rate. A diagnostic backend instrumented per layer/tier would be needed before another throughput intervention; no source change or new model measurement was made in this phase. The earlier 16→24-slot A/B remains the measured improvement, and no new performance claim is promoted.
