# C10b native ub64 server thermal failure

- Objective/base: 513-ID cold synthetic server request under E18 with P8 native ub64/preload ON, measurement commit `261b34a166132869681ab86e536081ad2aa97728`. Evidence class: physical guard failure, raw `results/c10b-20260927T1520Z/raw/c10b-g3-short513.*` local. C10b init and minimum forward had passed separately.
- Run: `systemd-run --user --scope -p MemoryMax=19327352832 -p MemorySwapMax=0 -- python3 tools/c10b_ub64_server.py results/c10b-20260927T1520Z --run short513 --measurement-commit 261b34a166132869681ab86e536081ad2aa97728`. CPU started at 49.5 C. At 75.848 s, sample CPU Tctl reached 95.125 C above the frozen 95 C guard. Watchdog terminated the server; scope elapsed 81.314 s, 72 samples, zero completed requests. Secondary HTTP disconnect is a consequence of termination, not an independent model error.
- Other observed peaks: RSS 15.173 GB, cgroup 15.007 GB, GPU total 3944 MiB, GPU 61 C, NVMe 48.85 C; zero swap/OOM/cgroup max events. This does not make ub64 numerically wrong or demonstrate slower/faster serving. No first-content or prefix-cache observation exists.
- Decision: `FAIL_RESOURCES_OR_EVIDENCE` for C10b's 513-ID unit. C9 ub32 had the same CPU95.125 C failure during the corresponding request. Strong current explanation is CPU thermal saturation in the server's full-SWA cold prefill; alternative is a workload/source hotspot not reduced by moving four layers. New C11 hypothesis: P12 placement plus existing native preload, at ub32, reduces CPU work/temperature. C7 P12 4K probe had GPU peak 5692 MiB and CPU peak 89.125 C over 189+32, but different workload/serving, so this is only feasibility evidence. Static accounting and new E18 init/forward admission precede any 513-ID test. Default unchanged.
