# M6 prospective fixed task comparison

Objective: measure whether GPT-OSS 120B delivers a verifiable advantage on the ten held-out synthetic tasks already fixed in `workloads/task_eval.jsonl`, compared with the best observed 20B stock placement. The task file was committed before target results. Two tune tasks remain separate and are not counted in the held-out score. Base lab commit `6ccd72a`. This is a functional comparison, not an optimization intervention or a new scientific novelty claim.

Run IDs and order are fixed: `task20b-stock-tune01`, `task20b-stock-eval01`, `task120b-stream24-tune01`, `task120b-stream24-eval01`. Tune runs test the request and grading path; their answers do not change the held-out tasks, validators, token cap or scoring. Each run has its own manifest and new server process.

Pre-measurement harness repair: `task20b-stock-eval01` never launched a server because the port guard rejected `TIME_WAIT` sockets from the preceding tune process. There was no task response or model run to score. A local bind with `SO_REUSEADDR` succeeds; the guard now uses that option, and the first actual stock evaluation run ID is `task20b-stock-eval02`. All model, workload, grading and resource conditions remain as frozen. The failed launch is retained in `DECISIONS.md`.

Grading-parser repair after the stock responses were saved, before target execution: the first report `task20b-stock-eval02-grade.json` marked two correct JSON payloads as `invalid JSON` solely because their final text was wrapped in a Markdown `json` code fence; `unwrap()` handled Python/SQL fences but omitted `json`. The fixed verifier strips that presentation fence and applies the same exact JSON fields and values from the frozen task file. It does not change prompts, model outputs, expected data, token cap or retry policy. Retain the initial grading failure and write a new report `task20b-stock-eval02-grade02.json`; the same fixed grader will score target responses.

Configuration fixed before execution: 20B stock SHA `4b1a27fa0eb875bbca4f6cfe936e3d65adc685c0`, verified 20B GGUF SHA `52f57ab7d3df3ba9173827c1c6832e73375553a846f3e32b49f1ae2daad688d4`, GPU14, direct loader, lazy mode off; target streaming SHA `1248fd8fa8cfebaece5ea992e4d951c1e18bb9d5`, verified 120B GGUF SHA `582bd40f6886200101f4c4ed9f25f3fe80cc14c86e9e2b37746cd8904a0c622d`, GPU8, 24 slots, O_DIRECT experts, no preload/repack. Both use the embedded official-compatible chat template, one context/parallel slot, context4096, batch256, microbatch32, eight CPU threads, greedy temperature0, seed42, explicit reasoning effort `medium`, no prompt cache, one attempt per task and max512 generated tokens. Server binds only to `127.0.0.1`. Runs are separate fresh processes in order 20B then 120B, with no simultaneous model runs. This compares task success under two identified configurations; different backend versions, model sizes and GPU placement prevent attributing all differences to parameter count alone.

Each server runs under an 18 GiB host cgroup and `memory.swap.max=0`, with RSS17 GiB, GPU7000 MiB and MemAvailable6 GiB watchdogs. Per-request timeout360 seconds; total timeout3600 seconds. Any OOM, swap, resource guard, missing provenance, backend error or incomplete response stops that run and is retained. The measurement is task success, total wall time to returned answer, prompt/completion tokens, and resource peaks; a separate streaming smoke records first received text, first reasoning text and first final-answer text latency where exposed by the API, without treating chunk spacing as token spacing. A truncation at the 512-token cap counts as failure unless a complete verifiable answer precedes it; no retries or changed token limits after observing outputs.

Scoring is predeclared from `validator` fields in the task file: code must pass listed assertions inside a local read-only/no-network `bubblewrap` namespace with CPU and wall timeout; SQL must return the specified rows from in-memory SQLite fixtures in the same isolated namespace; JSON extraction must parse and match fields; quantitative and planning answers must be checked against their exact numeric/constraint criteria and archived with the response. A case is `unknown` when the validator cannot confidently parse it, never silently counted as a pass. Report paired case outcomes, task categories, time and token tradeoffs; do not claim significance from ten cases. A larger-model advantage is observed only if more held-out cases pass with the same one-attempt policy and resource controls. Tests: NOT_RUN at freeze. Results local-only; no generated code or prompts from personal files are used.

Prospective secondary use of the target task run for M5: if the separate frozen CLI sustained run ends incomplete because its accumulating prefill reaches its 1800-second timeout, the target server task run may also be examined as a different named continuous-use configuration. It qualifies for the >=2 sustained decode gate only if all ten held-out requests complete, elapsed runtime is at least 900 seconds, unrounded backend decode timing is available for every request, total and last-half decoded-token rates are both >=2.000 tokens/s, and zero swap/OOM/watchdog events occur. Report all per-request rates, TTFT smoke, prefill, end-to-end and thermal windows. If these conditions do not hold, M5 remains unproven; no post-hoc workload trimming or threshold change. This server run keeps context4096 but disables prompt-cache reuse between independent requests, unlike the cumulative CLI conversation, so its rate is a separately identified configuration.
