Objective: select one executable stock/candidate pair and set a host/GPU budget before a heavy model run. Base Tesy commit: `7041b39ec42948e6d394e151974940750ba9b070`, branch `research/numerical-characterization-ab-20260925`, pre-existing untracked `.vscode/`. The lab is a separate repository. Evidence classes below: measured = local commands/headers; estimated = capacity calculation; unknown = no runtime measurement.

## Estimated initial budget (not measured peaks)

Host guardrail: leave about 6 GiB to OS/other processes and target <=26 GiB runtime, reduced when real availability is lower. Inventory availability of 24.08 GiB requires a lower practical ceiling at run time. Candidate 120B with 12 slots/layer needs 5,710,694,400 bytes (5.32 GiB) of streamed encoded weights in aggregate if all layers are placed on CPU; 16 slots need 7,614,259,200 bytes (7.09 GiB). The remaining resident BF16 tensors are 4,334,742,144 bytes (4.04 GiB) before backend representations. CPU placement could therefore start around 9.36 GiB for 12 slots, plus allocations, metadata, staging, page cache and workspace. Pinned memory has not been established. With 9 default I/O workers, staging is roughly 9 x (largest expert tensor slice plus 8192 bytes), or about 75 MiB; this is ordinary aligned memory, not proven pinned. Buffered reads can populate page cache and are not bounded by the nominal expert pool alone. No buffer is counted twice in the resident-weight sum; when a tensor is copied to VRAM, its page-cache/source presence must be measured separately.

GPU guardrail: 8188 MiB total, 12 MiB idle at inventory. If all 120B non-streamed BF16 tensors (4.04 GiB) and all 12-slot pools (5.32 GiB) were on GPU, their sum already exceeds VRAM. Layer partition and measured fixed allocations are required before choosing a GPU pool. GPU budget also needs KV, computation buffers, CUDA/backend allocations, other applications and free margin; no maximum number of GPU layers is asserted yet.

For a 4096-token, one-sequence *full* BF16 KV allocation, the architecture-based upper-bound calculation is 36 layers x 4096 positions x 8 KV heads x 64 dimensions x 2 (K,V) x 2 bytes = 301,989,888 bytes (288 MiB). Sliding-window allocation and backend padding may change the actual peak. It is not a number inferred from parameter count. Prefill and decode peaks are still unknown.

For 20B, 16 slots per each of 24 layers imply 5,076,172,800 bytes of encoded expert weights. GGUF size minus all expert weight tensors is 1,957,218,752 bytes (including biases/non-experts and file overhead). An all-CPU candidate floor is thus about 7.03 GB before staging/workspace/page cache. Stock all-CPU mapping can expose 12.11 GB to page cache. These are capacity estimates, not RSS or physical storage traffic.

## Alternatives, decision, tests and limitations

Alternative partition fork and other runtimes deferred until a concrete block. Chosen candidate exposes direct demand streaming of GGUF weights and wave prefill. No prediction or speculation. No code optimization has been made.

Tests completed: 20B full SHA-256 equals lock; 120B shard-header and offset checks pass; CMake CUDA configuration passes with GCC 15. CUDA configure with GCC 16 failed and remains a recorded failure. Model execution, numerical parity, two requests, 256-token decode, cgroup limits, I/O attribution and sustained thermals: NOT_RUN. Web search tool returned an authentication error; public Git refs were resolved by read-only `git ls-remote`.

Next discriminating gate: bounded candidate/stock 20B execution with resource monitoring, followed by fixed-prefix correctness. A 120B GGUF target of fixed revision/checksum or a separately validated native safetensors streaming backend is required for M4 on the existing local weights. No model is downloaded or converted by this lab.
